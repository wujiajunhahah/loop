# Loop — 香港 Physical Hackathon 项目背景与协作上下文

## 1. 项目背景

Loop 是一个准备参加香港 Physical Hackathon 的实体情感产品项目。

项目来自一个真实问题：当一个重要的人终将缺席时，人们往往直到很晚才意识到，很多声音、习惯、故事、关系细节和想说的话还没有被好好留下。普通录音笔、相册或聊天记录能够“保存数据”，但很难完成有对象、有选择、有时间条件、有托付感的关系传递。

Loop 不把“死亡”从产品中拿掉。死亡与终将缺席是产品成立的底层命题，也是区别于普通生活记录工具的关键。但产品不希望以沉重、恐惧或悲伤作为日常体验，而是用轻盈、日常、可接近的方式，让人提前思考：

> 当我无法继续亲自表达时，什么仍然代表我？我希望把它留给谁？我希望它如何陪伴对方？

产品不承诺帮助任何人“走出来”，不扮演救世主，也不替代亲人、家庭或专业支持。它提供的是由记录者本人提前设计、由接收者自主决定是否靠近的情感陪伴。

---

## 2. 核心产品定义

> Loop 是一个以“人终将缺席”为底层命题，通过生命记录、关系整理、主动设计与实体托付，让一个真实的人能够为特定对象留下可被重新触碰的关系 Context 和陪伴路径的系统。

它不是：

- 普通录音笔或云相册；
- 自由模拟逝者的人格聊天机器人；
- 自动判断用户悲伤并主动干预的设备；
- 强迫接收者完成遗愿或“走出去”的工具。

它是：

- 一套生命 Context 采集与整理系统；
- 一个按关系拆分、由本人授权的关系 Agent；
- 一个具有传承感、专属性和仪式感的实体入口；
- 一段由记录者提前设计、接收者自主继续的“未完待续”。

## 3. 当前产品共识

### 3.1 死亡议题的处理

- 保留死亡与终将缺席的命题重量；
- 降低谈论死亡的心理门槛；
- 不把产品视觉和交互做成纪念碑、遗嘱工具或悲伤装置；
- 可以使用假设性场景、游戏化引导和轻盈表达，但不消费悲伤。

### 3.2 记录者端

记录者在仍能亲自表达时，通过 App 和可穿戴硬件建立生命记录。

记录内容包括：

- 语音、文字、照片、影像；
- 人生经历、习惯、价值判断；
- 与不同对象的共同记忆；
- 只想留给某个人的话；
- 未来祝福、邀请与共同计划；
- 内容允许如何被 AI 使用的边界。

记录者不仅上传内容，还要完成：

- 什么代表我；
- 这段内容留给谁；
- 为什么留给他；
- 在什么情境下出现；
- 哪些只能原样播放；
- 哪些可以由 AI 整理；
- 哪些绝不能被生成或转述。

### 3.3 关系 Agent

Agent 必须按关系拆分，而不是生成一个通用人格。

同一个记录者可以有：

- 留给孩子的 Agent；
- 留给伴侣的 Agent；
- 留给朋友的 Agent。

Agent 的职责是：

- 管理公共 Context、关系专属 Context 和私密 Context；
- 避免内容配错对象；
- 检索、整理和编排本人确认过的真实素材；
- 根据日期、地点、天气、用户主动输入、共同计划进度等情境呈现内容；
- 管理“共同完成的一百件事”等关系延续计划；
- 接收接收者后来留下的新内容，让关系轨迹继续生长。

核心原则：

> AI 负责让记忆抵达，不负责替那个人继续发表新的意志。

### 3.4 互动原则

- 记录者可以主动设计未来陪伴；
- 接收者必须拥有最终主动权；
- 默认不主动打扰；
- 不在用户平静生活时突然播放强情绪内容；
- 可以在用户主动进入产品后，提供“有设计的偶遇”；
- 惊喜来自内容编排，不来自未经允许的骚扰；
- “共同做”是邀请，不是命令；
- 用户可以接受、延后、跳过或永久关闭。

### 3.5 硬件角色

当前优先路线：

> 戒指 + App + 云端 Agent

戒指不是完整对话设备，也不承担全部交互。

记录阶段：

- 戒指作为随身标记器；
- 用户通过触摸或动作标记“这一刻值得留下”；
- App 随后引导录音、拍照、输入对象和意义。

托付阶段：

- 戒指由记录者真实佩戴和使用；
- 之后被指定托付给某个接收者；
- 它作为专属物、关系凭证和 Agent 的实体钥匙。

接收阶段：

- 戒指负责触摸、佩戴、确认、轻震、灯光或身份触发；
- 复杂对话、影像、关系地图和计划管理发生在 App、耳机或底座；
- 硬件负责让互动有重量，软件负责让互动有深度。

HRV 等生理信号最多作为弱 Context，不作为“准确识别悲伤”的核心承诺。

## 4. MVP 演示闭环

1. 记录者佩戴戒指，并标记一个值得留下的时刻；
2. App 引导记录一段声音、照片或文字；
3. 用户选择接收对象，并补充“为什么留给他”；
4. 用户创建一段真实回忆，以及一个可选的未来共同计划；
5. 系统整理为对象专属关系 Agent；
6. 用户审核并确认 AI 使用边界；
7. 戒指被托付给接收者；
8. 接收者主动触摸戒指并进入 App；
9. Agent 根据当前 Context 呈现一段真实内容；
10. 接收者选择是否继续一项共同计划，并可留下新的记录。

推荐 Demo 场景：

> 母亲为女儿留下“五道家庭菜”的共同计划。女儿未来触摸母亲曾佩戴的戒指，在 App 中看到第一道菜的真实录音、故事和邀请。完成后，她上传自己的照片，关系轨迹点亮下一节点。

## 5. 技术架构方向

### 5.1 Context Capture Engine

负责：

- 多模态输入；
- 引导式提问；
- 对象、关系、时间、地点、主题和权限标注；
- 原始内容与 AI 整理内容区分；
- 记录者审核和确认。

### 5.2 Relationship Context Store

至少区分：

- public_persona：可代表“我是谁”的公共内容；
- relationship_specific：只属于某个对象的关系内容；
- private：不可分发或条件受限内容；
- planned_interactions：未来祝福、邀请、共同计划；
- policy：AI 可用范围、禁用范围、主动触发规则。

### 5.3 Agent Orchestration

负责：

- 按对象加载正确 Context；
- 检索与编排真实素材；
- 触景生情；
- 计划进度管理；
- 用户主动进入后的“有设计的偶遇”；
- 不越权生成未被授权的新意志。

### 5.4 Hardware Bridge

MVP 可先抽象为：

- NFC / BLE 身份绑定；
- 触摸或动作事件；
- LED / vibration 反馈；
- 与 App 的触发协议；
- 硬件不可用时的软件模拟器。

### 5.5 API

黑客松提供了可高频调用的 API 配额，已计划通过 OpenCode 调用。

要求：

- 所有密钥通过环境变量管理；
- 不把 API Key 写入仓库；
- 为 API 调用封装统一 Adapter；
- 保留 mock，避免现场网络或接口异常导致 Demo 失效；
- 即使额度充足，也记录请求类型、错误和成本估计，避免无意义重复调用。

## 6. 本地协作环境

项目主目录：

```text
D:\Codex-Workspace\Loop
```

协作方式：

- Codex 桌面版打开该目录，用于总览、架构审查、任务拆解、状态同步和集成判断；
- OpenCode 是主要执行环境；
- 多个 OpenCode 窗口可并行工作；
- 所有实际开发、测试和提交主要在 OpenCode 中完成；
- Codex 桌面版默认不与 OpenCode 重复实现同一任务。

推荐项目内协作目录：

```text
.loop/
  STATUS.md
  DECISIONS.md
  RISKS.md
  INTEGRATION_QUEUE.md
  tasks/
  claims/
  reports/
```

多窗口并行原则：

- 一个窗口只领取一个明确任务；
- 不允许多个窗口同时修改同一组核心文件；
- 优先使用独立 Git 分支或 worktree；
- 每个窗口创建唯一 session_id；
- 每次提交后写 session report；
- 架构变更先写 Decision Request，不直接在多个窗口中各自改架构；
- Codex 桌面版负责聚合进度，不作为默认编码窗口。

## 7. 当前优先级

P0：

- 打通最小 Context 录入；
- 建立关系对象与权限模型；
- 完成一个对象专属 Agent；
- 完成一个戒指触发模拟；
- 跑通“记录—托付—触发—呈现—继续计划”的 Demo。

P1：

- 多模态输入；
- 触景生情；
- 关系轨迹可视化；
- 共同计划与内容解锁；
- 真实硬件接入。

P2：

- 一对多关系；
- 更多专属物载体；
- HRV 等弱状态信号；
- 家庭协作；
- 长期云端运营能力。

---

## 8. 一句话版本

> 记录者设计未来如何陪伴，Agent 让真实内容恰当地出现，接收者决定是否打开，硬件让这份关系真正被托付。
